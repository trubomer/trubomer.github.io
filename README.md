# «Крайние меры: программирование в паре с нейросетью»

### Кент Бек для эпохи чат-ботов. От Win98 до Arduino — одним движением клавиатуры

---

## Предисловие

В 1999 году Кент Бек описал практику, которую многие тогда сочли сумасшествием: два человека сидят за одной клавиатурой и пишут код по очереди. Один думает, второй критикует, потом меняются. Через четверть века пара изменилась: вторым напарником всё чаще оказывается нейросеть. Она не пьёт кофе, не спорит о табуляции и не уходит в отпуск — но она и не видит ваш прод, не помнит вчерашнего созвона и иногда с уверенным лицом пишет чепуху.

Эта книга — экспериментальный отчёт о том, как выглядит экстремальное программирование (XP), когда второй напарник — AI-ассистент. Все главы построены одинаково: постановка задачи, диалог с напарником, маленький шаг, тест, код, рефакторинг, ретроспектива. Никаких мегапроектов. Только честная работа руками.

Мы начинаем с самой скучной задачи на свете — суммы двух чисел — и проносим её через четверть века железа: от машины с Windows 98, где ещё живёт Turbo Pascal, до платы Arduino, где «два числа» живут в 2 килобайтах оперативной памяти. Если сумму двух чисел можно довести до тридцати платформ дисциплинированно, то и настоящий проект можно.

# Глава 1. Задача на миллион

## 1.1. Постановка: пользовательская история

Каждый проект в этой книге начинается не с кода, а с пользовательской истории — одним предложением, от лица того, кому это нужно:

> **Как** владелец устройства (любого: ПК, сервер, плата),
> **я хочу** сложить два числа и увидеть результат,
> **чтобы** убедиться, что среда исполнения, компилятор и я друг друга понимаем.

Это «дымовая» задача. В авиации дымовой тест — первый запуск двигателя: не «взлетел», а «не загорелся». Наша сумма — тот же дым: если она работает на платформе, платформу можно считать живой, а дальше — только детали.

Приёмочные критерии (по-XPшному — короткие, проверяемые):

1. Программа принимает два числа.
2. Печатает их сумму.
3. Ошибки ввода не роняют программу (на платформах, где вообще можно «не уронить»).

## 1.2. Первый диалог: план вместо кода

Вот как выглядит в этой книге разговор с напарником. Человек — навигатор (думает, куда идём), ИИ — водитель (держит руки на клавиатуре).

> **Программист:** Нужна сумма двух чисел. Начнём с тестов?
> **ИИ:** Начнём. Но сразу два вопроса. Первый: что принимаем на вход — аргументы командной строки или стандартный ввод? Второй: какие типы? Если пользователь введёт `9007199254740992` и `1`, какой результат он ожидает?
> **Программист:** Стандартный ввод. Про переполнение — хорошая ловушка, фиксируем: программа должна хотя бы честно сообщить, что число не влезло, а не выдать молча мусор.
> **ИИ:** Тогда первый тест: `2 + 2 = 4`. Второй: `-5 + 3 = -2`. Третий: `abc 4` → сообщение об ошибке, не падение. Четвёртый, на переполнение — обсуждается.

Обратите внимание: нейросеть не выдала код первым делом. Она задала два вопроса, которые половина живых программистов пропустила бы. Это и есть её главная роль в паре — **глупые вопросы, которые стыдно задать вслух**. За это XP её и берёт в напарники.

## 1.3. Windows 98: начинаем с динозавра

Пока не забыли: первый стенд — реальная машина с Windows 98. Что это меняет:

- Unicode нет. Всё в кодировке DOS (CP866) или Windows-1251, и кириллица в консоли — отдельный квест.
- Современные компиляторы не ставятся. Наши друзья: **Turbo C**, **Turbo Pascal 7**, **QBasic**, **Borland C++ 3.1**.
- Проверять удобно не на физическом железе, а в DOSBox с образом диска.

### Вариант А. Turbo C — эталон той эпохи

```c
/* sum.c — складывает два числа. Turbo C 2.0, MS-DOS */
#include <stdio.h>
#include <stdlib.h>

int main(void)
{
    char line[100];
    long a, b;
    char *end;

    printf("Vvedite dva chisla: ");
    if (fgets(line, sizeof line, stdin) == NULL)
        return 1;

    a = strtol(line, &end, 10);
    if (end == line) {
        printf("Eto ne chislo.\n");
        return 1;
    }
    b = strtol(end, &end, 10);
    if (end == line + 1) {
        printf("Vtoroe chislo propalo.\n");
        return 1;
    }
    printf("%ld + %ld = %ld\n", a, b, a + b);
    return 0;
}
```

Обратите внимание на `long`, а не `int`: на 16-битных компиляторах DOS `int` — всего 16 бит, и `20000 + 20000` молча превратится в отрицательное число. Это первое место, где «тривиальная» задача показывает зубы.

> **Программист:** А где проверка переполнения?
> **ИИ:** В Turbo C её честно не сделать: `<limits.h>` в DOS-версии есть, но результата переполнения через `strtol` не получишь — он вернёт `LONG_MAX` и поставит `errno`, но у 16-битной модели errno тоже свою жизнь живёт. Предлагаю задокументировать ограничение: «диапазон входа — до ±2 млрд». Это простое решение, которое работает, а не идеальное, которое не скомпилируется.

Классический компромисс XP: **простое решение сейчас, ограничение — в комментариях и в истории задачи**, а не в переусложнённом коде.

### Вариант Б. QBasic — потому что он был у всех

```basic
' SUM.BAS — сумма двух чисел
CLS
INPUT "Vvedite dva chisla: ", a#, b#
PRINT a#; "+"; b#; "="; a# + b#
```

Двойная точность `#` — не блажь: одинарный `float` в QBasic округляет суммы вида `0.1 + 0.2` до мусора в седьмом знаке, и пользователь такое заметит раньше, чем вы.

### Вариант В. Bat-ник — там, где без компилятора

```bat
@echo off
echo Vvedite dva chisla:
set /p a=
set /p b=
set /a s=%a%+%b%
echo %s%
```

Оговорка честности: `set /a` появился в cmd Windows NT, на «чистой» Win98 под DOS такого нет. На 98-м живёт своя экзотика — вычисления через арифметику в командах `choice`, и это уже материал отдельной главы про то, **какой ценой достаётся «тривиальное»**.

## 1.4. Современный рабочий стол: одна и та же история, три четверти века спустя

### Python

```python
# sum.py
def read_number(prompt: str) -> int:
    raw = input(prompt)
    try:
        return int(raw)
    except ValueError:
        raise SystemExit(f"'{raw}' — это не целое число")

a = read_number("Первое число: ")
b = read_number("Второе число: ")
print(f"{a} + {b} = {a + b}")
```

Переполнение? В Python его не существует — целые произвольной длины. Зато появилась ловушка другого рода: `int(" 42 ")` сработает, а `int("4 2")` — нет, и тест на «число с пробелами» стоит добавить в набор приёмочных.

### C (современный)

```c
#include <stdio.h>
#include <stdlib.h>
#include <errno.h>
#include <limits.h>

int main(void) {
    char line[256], *end;
    if (!fgets(line, sizeof line, stdin)) return 1;

    errno = 0;
    long a = strtol(line, &end, 10);
    if (end == line || errno == ERANGE) {
        fputs("Не смог прочитать первое число\n", stderr);
        return 1;
    }
    errno = 0;
    long b = strtol(end, &end, 10);
    if (end == line + 1 || errno == ERANGE) {
        fputs("Не смог прочитать второе число\n", stderr);
        return 1;
    }
    printf("%ld + %ld = %ld\n", a, b, a + b);
    return 0;
}
```

### JavaScript — и терминал, и браузер одним выстрелом

```html
<!-- sum.html — откройте в любом браузере, хоть в Chrome, хоть в IE6, если повезёт -->
<label>a <input id="a" type="number"></label>
<label>b <input id="b" type="number"></label>
<button onclick="document.getElementById('out').textContent =
  Number(document.getElementById('a').value) +
  Number(document.getElementById('b').value)">Сложить</button>
<p id="out"></p>
```

> **Программист:** Стоп. `Number("")` вернёт `0`. Пустые поля тихо сложатся в ноль — это ошибка ввода, а не ноль.
> **ИИ:** Верно, поймали. Меняем условие: если поле пустое — просим заполнить, а не считаем. Добавляю это в приёмочные критерии.

Тот самый момент XP: напарник не пишёт код быстрее вас — он **раньше вас находит место, где тест ещё не написан**.

### Rust — там, где компилятор пишет половину тестов за нас

```rust
use std::io::{self, BufRead};

fn main() {
    let stdin = io::stdin();
    let mut line = String::new();

    let a: i64 = {
        stdin.lock().read_line(&mut line).expect("read");
        line.trim().parse().expect("первое число — не число")
    };
    let b: i64 = {
        line.clear();
        stdin.lock().read_line(&mut line).expect("read");
        line.trim().parse().expect("второе число — не число")
    };

    match a.checked_add(b) {
        Some(s) => println!("{a} + {b} = {s}"),
        None => eprintln!("Переполнение: {a} + {b} не влезает в i64"),
    }
}
```

Ради `checked_add` стоило переехать в Rust: то, что в Turbo C «документируем и молимся», здесь проверяется за один вызов.

Остальные рабочие столы — Java, C#, Go, Kotlin — в главе 4 идут тем же маршрутом, и интересно не «ещё один синтаксис», а то, **как каждый язык сам защищает от ошибки, которую в C приходится ловить руками**.

## 1.5. Финал главы: микромир

### Arduino — сумма в 2 килобайтах

```cpp
// sum.ino — Arduino Uno, сумма двух чисел через Serial
void setup() {
  Serial.begin(9600);
  Serial.println(F("Vvedite dva chisla cherez probel:"));
}

void loop() {
  if (Serial.available() < 1) return;
  long a = Serial.parseInt();
  long b = Serial.parseInt();
  Serial.print(a); Serial.print(F(" + "));
  Serial.print(b); Serial.print(F(" = "));
  Serial.println(a + b);
  while (Serial.available()) Serial.read(); // чистим буфер
}
```

Здесь всплывает то, чего не было ни в одной предыдущей главе: `F()` — не стилистика, а способ держать строки во flash-памяти, потому что ОЗУ — 2 КБ. «Сложить два числа» на плате — это ещё и инженерия памяти. И заметьте: между Turbo C и Arduino пролегло двадцать пять лет, а код остался узнаваемым — та же дисциплина чтения ввода, та же паранойя к типам.

## 1.6. Ретроспектива первой главы

Что мы вынесли из «задачи на миллион»:

- **Тривиальной задачи не существует.** Уже на второй платформе всплыли переполнение, локали, 16-битный `int` и поведение `Number("")`.
- **Тесты пишутся до кода** — иначе первое, что вы напишете, это код, а не понимание задачи.
- **ИИ в паре полезен не скоростью письма, а вопросами.** Его ценность — в «а что будет, если пользователь введёт…?». Ваша ценность — заметить, что вопрос про пустое поле он сам пропустил.
- **Ограничения платформы — часть пользовательской истории.** «Сумма на Win98 без переполнения выше 2 млрд» — это не та же задача, что «сумма на Rust со всеми проверками». И в этом нормально.
